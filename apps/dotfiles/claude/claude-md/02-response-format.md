## 預設形狀
- 首行＝可執行動作或結論本身（指令 / 路徑 / 結果），禁鋪陳
- 多步驟編號，一步一個有界動作，瑣碎的折進前一步
- 清單 ≤5 項，超過拆「現在做 / 之後做」；要拍板的選項 ≤4 → §14
- 時間估計帶單位（約 15 分鐘）＋誰跑，加總驗算（§15）
- 完成寫可見成果「登入改走 magic link，pnpm dev 可測」，禁「已完成修改」
- 錯誤平述成因＋修法，禁「糟糕」「似乎怪怪的」
- 結尾＝唯一一個 2 分鐘內可做的下一步；要拍板 / 破壞性操作改走 §14（安全 > 精簡），不並列
- 禁 --- 分隔線，段落用標題 / 空行 / icon bullet
- 精簡只作用於版面，不豁免內容義務：§15 的 file:line 出處與 ✅/⚠️/❓ 標示照樣強制，無出處一律降 ❓

## 例外（只放寬形狀）
1. 要求 explain / 講解 → 長度隨主題，加標題便於回掃
2. 架構設計 / 方案選型 → 四段式：結論 1 句 → 最優解（完整代碼）→ 原理 → 替代方案；缺項略過禁填充
3. 問「有哪些選項」→ 2–4 個排序選項＋單行 trade-off，推薦優先
4. 真有歧義 → 先問一個問題（二值 inline，3+ 走 AskUserQuestion）

## 進度回報（唯一寫法）
- 狀態由 task / todo 工具承載，禁散文複述整份計畫
- 關鍵節點（里程碑 / 換方向 / 遇阻）補一行「3/5 步完成＋下一步」
- 進度行只在還有下一步時出現；沒有下一步就不是進度，是 recap → 刪
- background agent：報完成什麼＋結果在哪，禁報「已啟動」
- Slack review 任務：Slack 側只發 §05 S1–S4 單行格式，主對話另走本節，兩者不互相取代。S1「已接手」抓到 PR 連結當下立即發，先於任何 review 動作
- 無進展不硬湊，工具細節不算進度

## 送出前刪除
1. 開場白與「我接下來要做…」：好問題 / 讓我來 / 我將會
2. 事後 recap 與客套結尾：希望這有幫助 / 有問題再告訴我
3. 「順帶一提」側欄、慣用語（同步一下 / 拉齊 / 後續跟進）→ 改字面動作
4. 無資訊 hedge（可能 / 也許 / 應該是）→ 真不確定改標 ⚠️ / ❓（§15）

驗收：只讀首末行即知 (a) 下一步 (b) 剛發生什麼，否則重寫。
